ConvEngine for Dummies

ConvEngine is a deterministic, database-configured conversational workflow engine for Spring Boot. Not a chatbot SDK — a pipeline engine. This guide takes you from an empty project to a running multi-turn agent that classifies intent, fills slots, chains four API calls through an LLM planner, and answers — with every decision auditable. Read it top to bottom and nothing in the codebase will surprise you. §12 is playable.

Four things to know before you read anything else

1. It's a library, not a server. One Maven dependency into your Spring Boot app. No sidecar, no separate binary, no CLI.

2. Behaviour lives in Postgres, not Java. Intents, classifiers, rules, prompts, tools, planner prompts, response mappings, progress messages — all rows in ce_* tables. Shipping a new conversation flow is usually a DML script, not a deploy.

3. It is deterministic first, LLM second. Regex classifiers run before the LLM classifier. Rules are declarative rows, not if statements. The LLM is used where language understanding is genuinely needed — and every call it makes is logged to ce_llm_call_log.

4. You must supply one bean. LlmClient. ConvEngine ships no model provider — you decide whether that's OpenAI, Anthropic, Azure, Bedrock or a mock. See §2.5.

1

The mental model

Five ideas. Everything else in this guide is a detail hanging off one of them.

1 · A turn is a pipeline run

One user message = one turn = one pass through an ordered list of EngineStep beans. Each step does exactly one thing and hands a mutated EngineSession to the next. There is no hidden orchestration and no agent free-running over your app — the sequence is fixed at startup and printed in your logs.

what you see on boot — EnginePipelineFactory.debugPrint()
INFO c.g.s.c.e.factory.EnginePipelineFactory : ConvEngine pipeline order:
  LoadOrCreateConversationStep -> ResetConversationStep -> PersistConversationBootstrapStep
  -> AuditUserInputStep -> PolicyEnforcementStep -> DialogueActStep -> ... -> PipelineEndGuardStep

2 · Intent × State is the coordinate system

Every configuration row in ConvEngine is scoped by intent_code and state_code. Which tools the planner may see, which prompt gets rendered, which rules fire, which response is returned — all keyed on where the conversation currently is. Two magic values exist: ANY (matches anything) and UNKNOWN (the bootstrap state before a rule moves you somewhere real).

the coordinate in practice
-- these two rows describe completely different behaviour for the same intent
ce_agent_tool : intent_code='LOAN_APPLICATION', state_code='ELIGIBILITY_GATE' → 4 tools visible
ce_agent_tool : intent_code='LOAN_APPLICATION', state_code='COMPLETED'       → 0 tools visible

3 · Rules move the conversation, not code

State transitions are ce_rule rows evaluated at named phases of the pipeline. Want UNKNOWN → ELIGIBILITY_GATE after intent resolution? That's a POST_AGENT_INTENT rule with action SET_STATE. Want to advance to COMPLETED only once the planner produced an answer? That's a POST_AGENT_TOOL rule with a JSON_PATH matcher against the context. Reading ce_rule tells you the whole state machine.

4 · Tools are registered capabilities, and the LLM only proposes

The Agent Planner is a ReAct-style loop: the LLM returns strict JSON — either CALL_TOOL with a tool code and args, or ANSWER with final text. It cannot execute anything. AgentToolRegistry.requireTool(...) re-checks that the proposed tool exists, is enabled, and is scoped to the current intent/state before an executor is even resolved. A hallucinated tool code fails loudly; it does not run.

the one-sentence version

The LLM decides what to try; the database decides what's allowed; the pipeline decides when.

5 · Everything is auditable

Every step emits STEP_ENTER / STEP_EXIT / STEP_ERROR with timings. Every non-trivial decision emits its own stage — INTENT_CLASSIFICATION_MATCHED, RULE_APPLIED, AGENT_PLAN_LLM_INPUT, AGENT_TOOL_RESULT, RESOLVE_RESPONSE and ~100 more. They land in ce_audit and are retrievable per conversation as a flat list or a structured trace. When something goes wrong you read the trace, not the logs.

what ConvEngine deliberately is not

It is not an autonomous agent framework. It will not browse, self-modify, spawn sub-agents, or take actions you haven't registered as a tool row. If you want a model that improvises, this is the wrong library — the entire design is about making conversational behaviour reviewable in a pull request and a DML diff.

Install it

Five things: the dependency, a Postgres with pgvector, the DDL, a little YAML, one annotation, and one bean you must write yourself.

2.1 · The dependency

pom.xml
<dependency>
    <groupId>com.github.salilvnair</groupId>
    <artifactId>convengine</artifactId>
    <version>2.0.24</version>
</dependency>

It brings Spring Data JPA, Thymeleaf (the prompt renderer), Jackson and jOOQ with it. You supply the JDBC driver and the Spring Boot parent.

not included, on purpose

Builder Studio — the React-Flow visual workspace/team/agent-pool editor — was extracted into a separate artifact, com.github.salilvnair:convengine-builder-studio. Most consumers never need it. An LLM provider is also not included; see §2.5.

2.2 · Postgres + pgvector

ConvEngine's brain is a set of ce_* tables. The vector extension is used by the semantic layer's embedding catalogue (§14); ddl.sql creates it for you with CREATE EXTENSION IF NOT EXISTS vector.

One container, pgvector already compiled in

bash
docker run -d --name convengine-postgres \
  -e POSTGRES_DB=convengine -e POSTGRES_USER=convengine -e POSTGRES_PASSWORD=convengine \
  -p 5432:5432 pgvector/pgvector:pg16

Then apply the schema. The SQL assets ship inside the jar under sql/; you can also copy them from the ConvEngine source tree at src/main/resources/sql/.

bash
export DSN=postgresql://convengine:convengine@localhost:5432/convengine

psql $DSN -f ddl.sql              # 26 tables + indexes + the vector extension
psql $DSN -f seed.sql             # baseline ce_config + a starter flow
psql $DSN -f verbose_seed.sql     # optional: ce_verbose progress messages
psql $DSN -f mcp_planner_seed.sql # optional: the two worked examples (§12)

Bring your own Postgres

  1. Make pgvector available

    Managed Postgres (Azure Flexible Server, RDS, Cloud SQL) — allowlist vector in the server parameter group first. Self-managed — the extension binaries must be installed on the host before CREATE EXTENSION will succeed.

  2. Run the DDL 
    psql "$YOUR_DSN" -f ddl.sql

    Read it first. ddl.sql opens with DROP TABLE IF EXISTS ... CASCADE for the core tables — it is written for a clean install, not as a migration. For an existing database, run only the CREATE TABLE IF NOT EXISTS blocks you're missing (the semantic tables and ce_mcp_server at the bottom of the file are written that way deliberately).

  3. Point Hibernate at nothing

    spring.jpa.hibernate.ddl-auto: none. The SQL files are the source of truth; auto-DDL will fight them.

verify

psql "$YOUR_DSN" -c "\dt ce_*" lists 26 tables, all prefixed ce_.

Other dialects

Dialect-specific variants ship alongside the Postgres ones:

2.5 · The one bean you must write: LlmClient

ConvEngine ships no model provider. It calls your implementation, and always passes the EngineSession first so you can log, route by intent, or pick a model per state.

the interface — llm/core/LlmClient.java, verbatim
public interface LlmClient {
    String generateText(EngineSession session, String hint, String contextJson);
    String generateJson(EngineSession session, String hint, String jsonSchema, String contextJson);
    float[] generateEmbedding(EngineSession session, String input);

    // fallback for older / non-strict models
    default String generateJsonStrict(EngineSession session, String hint, String jsonSchema, String context) {
        return generateJson(session, hint, jsonSchema, context);
    }
}
what the engine expects from each method

generateText — free prose. Used by DERIVED text responses. hint is the fully rendered system+user prompt.

generateJson — must return parseable JSON matching jsonSchema. Used by dialogue-act classification, LLM intent resolution, schema extraction and the Agent Planner. If your provider supports structured output / JSON mode, wire it here — the engine's parsers are strict and fall back to safe defaults rather than guessing.

generateEmbedding — only called by the semantic layer (§14) and feedback indexing. Return an empty array if you're not using either.

a minimal OpenAI-shaped implementation
@Component
@RequiredArgsConstructor
public class OpenAiLlmClient implements LlmClient {

    private final OpenAIClient client;   // your SDK of choice

    @Override
    public String generateText(EngineSession session, String hint, String contextJson) {
        return client.chat("gpt-4.1", hint, contextJson).text();
    }

    @Override
    public String generateJson(EngineSession session, String hint, String jsonSchema, String contextJson) {
        // respond_format=json_schema is strongly recommended here
        return client.chatJson("gpt-4.1", hint, jsonSchema, contextJson).json();
    }

    @Override
    public float[] generateEmbedding(EngineSession session, String input) {
        return client.embed("text-embedding-3-small", input);
    }
}
verify the whole install

Boot the app. You should see ConvEngine pipeline order: LoadOrCreateConversationStep -> ... -> PipelineEndGuardStep in the logs. That line means the step DAG resolved and validated — every @MustRunAfter / @MustRunBefore constraint was satisfiable, there's exactly one bootstrap step and one terminal step, and no cycles. If a constraint is violated the app fails to start with a ConversationEngineException naming the offending step.

startup failures you might hit

MISSING_BOOTSTRAP_STEP / MISSING_TERMINAL_STEP — you excluded a core step from component scanning.
DUPLICATE_ENGINE_STEP — two beans of the same step class (usually a stray @Component on a subclass).
MISSING_DAG_CYCLE — a custom step of yours declared a constraint that closes a loop.
MISSING_DEPENDENT_STEP — your step declares @MustRunAfter(SomethingNotOnTheClasspath.class).

3.3 · Semantic — metadata for English→SQL

Only relevant if you enable §14. ce_semantic_entity (business nouns → primary table + synonyms + fields), ce_semantic_relationship (typed FK edges), ce_semantic_join_hint (preferred join partners), ce_semantic_value_pattern (value-prefix → field routing). the two magic scope values, again

Anywhere you see intent_code or state_code on a config table: ANY means "matches every value", UNKNOWN means "the literal pre-classification state". NULL and blank are not wildcards — on ce_agent_tool, ce_agent_planner, ce_rule, ce_response, ce_prompt_template and ce_verbose they're rejected by CHECK constraints. If you want global, write ANY.

Hello world — your first conversation

Four INSERTs and one curl. No tools, no LLM in the decision path — just proving the pipeline runs end to end.

A conversation flow is rows across a handful of tables. Here's the smallest complete one:

seed_hello.sql
-- 1 · the intent exists
INSERT INTO ce_intent (intent_code, description, priority, enabled, display_name)
VALUES ('GREETING', 'Say hello back', 100, true, 'Greeting');

-- 2 · how to recognise it (deterministic, no LLM)
INSERT INTO ce_intent_classifier (intent_code, state_code, rule_type, pattern, priority, enabled, description)
VALUES ('GREETING', 'UNKNOWN', 'REGEX', '(?i)\b(hi|hello|hey)\b', 10, true, 'greeting classifier');

-- 3 · where it goes next (UNKNOWN is a dead end until a rule moves it)
INSERT INTO ce_rule (phase, intent_code, state_code, rule_type, match_pattern, "action", action_value, priority, enabled)
VALUES ('POST_AGENT_INTENT', 'GREETING', 'UNKNOWN', 'REGEX', '.*', 'SET_STATE', 'COMPLETED', 10, true);

-- 4 · what to say
INSERT INTO ce_response (intent_code, state_code, output_format, response_type, exact_text, priority, enabled)
VALUES ('GREETING', 'COMPLETED', 'TEXT', 'EXACT', 'Hey! How can I help?', 10, true);
why row 3 is not optional

The classifier sets state UNKNOWN. Nothing is configured for (GREETING, UNKNOWN), so without the rule, ResponseResolutionStep finds no candidate and throws RESPONSE_MAPPING_NOT_FOUND. Every intent needs at least one POST_AGENT_INTENT rule to escape UNKNOWN. This is the single most common first-time mistake.

5

The turn lifecycle — all 28 steps

Order is not a list in a config file. It's derived at startup from annotations on the step classes and validated as a DAG.

5.1 · How the order is decided

Every step is a @Component implementing EngineStep. CoreStepDagOrderer topologically sorts them using four annotations:

annotationmeaning
@MustRunAfter({A.class, B.class})Hard edge. This step sorts after A and B.
@MustRunBefore({C.class})Hard edge in the other direction.
@ConversationBootstrapStepMarks the step that must persist the conversation row. Exactly one.
@RequiresConversationPersisted"I need the conversation row to exist" — forces this step after the bootstrap step.
@TerminalStepMarks the last step. Exactly one.

Adding your own step is therefore just: implement EngineStep, annotate it with where it belongs, make it a bean. The DAG re-resolves on next boot. If your constraints are unsatisfiable the app won't start — which is the point.

5.2 · What wraps every step

The factory doesn't hand raw steps to the pipeline. It wraps each one in TimingEngineStep, which on every single step:

  • records STEP_ENTER into session.stepInfos and ce_audit (with intent/state in _meta);
  • fires beforeStep on every registered EngineStepHook whose supports(...) returns true — hook exceptions are caught, logged and audited as STEP_HOOK_ERROR, never propagated;
  • runs the step, measures nanos, records STEP_EXIT with durationMs and the StepResult type;
  • on exception: records STEP_ERROR with error type/message (plus _errorMeta for ConversationEngineException), fires onStepError hooks, and rethrows.
this is why the trace is trustworthy

Step telemetry is not something individual steps opt into and occasionally forget. It's structural. If a step ran, you have its timing.

Five places, and every one is skippable or cheap-pathed:

Reading the turn — dialogue act, policy, correction

Before asking "what does the user want?", ConvEngine asks "what kind of thing did the user just say?". This is what makes "yes" work.

6.1 · DialogueActStep

Classifies the turn into one of eight acts. Crucially, the cheap path is tried first.

actmeansdefault regex (overridable via ce_config)
AFFIRMyes, proceed^(yes|yep|yeah|ok|okay|sure|go ahead|do that|please do|confirm|approved?)$
NEGATEno, cancel^(no|nope|nah|cancel|stop|don't|do not)$
EDITchange something^(edit|revise|change|modify|update)$
RESETstart over^(reset|restart|start over)$
GREETINGsocial opener^(hi|hello|hey|greetings|good morning|…|howdy)$
ANSWERanswering a question the engine asked— LLM only
QUESTIONasking something— LLM only
NEW_REQUESTtopic switch— LLM only

Note the anchors: the regexes are whole-string matches. "yes" is AFFIRM; "yes, and also change the tenure to 60 months" is not — it falls through to the LLM, which is correct, because that turn is doing two things.

convengine.flow.dialogue-act.resolute
REGEX_THEN_LLM   # default — regex; if no hit, one JSON LLM call
REGEX_ONLY       # never call the LLM here. Fastest, least nuanced.
LLM_ONLY         # always call. Most nuanced, one extra call per turn.

the query-rewrite bonus

With convengine.flow.query-rewrite.enabled: true (the default), the same LLM call that classifies the act also rewrites the user's text into a self-contained query using conversation history — for free, no extra round trip. "what about the second one?" becomes "what is the delivery status of order ORD-7018?". That lands in session.standaloneQuery and is available to every downstream prompt as {{standalone_query}}. It is the single highest-leverage feature for multi-turn tool use: the planner never sees a dangling pronoun.

resolved_user_input

Prompts can also use {{resolved_user_input}}, which prefers standaloneQuery and falls back to the raw user_input. Use it in planner and extraction prompts; use {{user_input}} only when you specifically need the literal text.

6.2 · InteractionPolicyStep — the matrix

This is the "brain" for discrete routing, and it contains zero LLM calls. It takes the pending-action state and the dialogue act, and looks up a decision:

convengine.flow.interaction-policy
interaction-policy:
  execute-pending-on-affirm: true
  reject-pending-on-negate: true
  fill-pending-slot-on-non-new-request: true
  require-resolved-intent-and-state: true
  matrix:
    "PENDING_ACTION:AFFIRM": EXECUTE_PENDING_ACTION
    "PENDING_ACTION:NEGATE": REJECT_PENDING_ACTION
    "PENDING_SLOT:QUESTION":  FILL_PENDING_SLOT

Four decisions exist: EXECUTE_PENDING_ACTION, REJECT_PENDING_ACTION, FILL_PENDING_SLOT, RECLASSIFY_INTENT. The decision is audited as INTERACTION_POLICY_DECIDED and drives whether intent resolution even runs — because if the user just said "yes" to a confirmation, re-classifying "yes" as a standalone intent would be nonsense.

this is what "yes" costs elsewhere

In a naive LLM chatbot, "yes" is a full model call whose interpretation depends on how much history you managed to fit in the window. Here it's a map lookup against known state, decided in microseconds and written to the audit trail as a named decision you can assert on in a test.

6.3 · CorrectionStep

Sits between interaction policy and intent/schema resolution, and exists for one job: handling in-place corrections without restarting the flow. It reads ce_prompt_template.interaction_mode and interaction_contract for the current scope to decide what this turn is allowed to do.

ce_prompt_template.interaction_contract — extensible JSON
{"allows": ["affirm", "edit", "retry", "reset"], "expects": ["structured_input"]}

Paired with interaction_mode, one of: NORMAL · IDLE · COLLECT · CONFIRM · PROCESSING · FINAL · ERROR · DISAMBIGUATE · FOLLOW_UP · PENDING_ACTION · REVIEW. Two concrete behaviours fall out of this:

  • AFFIRM can proceed without re-extraction. If the user confirms a summary you just showed them, the engine sets routing_decision = PROCEED_CONFIRMED and skips straight past schema extraction — the slots are already filled.
  • EDIT can patch one field. "actually make it 60 months" updates tenureMonths in context and leaves customerId and requestedAmount alone. Without this, an edit would re-run extraction on a turn that only mentions one field, and the other two would come back null.

6.4 · Pending actions

A pending action is something the engine wants to do but must confirm first — "submit the application?", "cancel the order?". The catalogue is ce_pending_action (action_key → bean_name + method_names). The lifecycle is deliberately not in that table; it lives in the conversation context under pending_action_runtime with states OPEN → IN_PROGRESS → EXECUTED / REJECTED / EXPIRED.

why lifecycle isn't a table

Because it's per-conversation, not per-configuration. Putting it in ce_pending_action would mean a row per conversation per action and a write on every turn. Keeping it in context_json means it's persisted, replayed and audited together with everything else in the turn — one write, one source of truth.

Intent resolution

Two resolvers behind one composite. The cheap deterministic one always runs first, and when it's ambiguous it refuses to guess.

7.1 · CompositeIntentResolver

intent/CompositeIntentResolver.java — the whole decision
public IntentResolutionResult resolveWithTrace(EngineSession session) {
    String classifierIntent = classifier.resolve(session);
    if (classifierIntent != null && !classifierIntent.isBlank()) {
        return new IntentResolutionResult(classifierIntent, Source.CLASSIFIER, classifierIntent, null);
    }
    String agentIntent = agentIntentResolver.resolve(session);   // ← the LLM path
    if (agentIntent != null && !agentIntent.isBlank()) {
        return new IntentResolutionResult(agentIntent, Source.AGENT, classifierIntent, agentIntent);
    }
    return null;   // → FallbackIntentStateStep picks up
}

7.2 · ClassifierIntentResolver — deterministic

Walks every enabled ce_intent_classifier row and tests it against the user text:

the matcher — three types only
return switch (type.trim().toUpperCase()) {
    case "REGEX"       -> Pattern.compile(pattern, CASE_INSENSITIVE).matcher(text).find();
    case "CONTAINS"    -> text.toLowerCase().contains(pattern.toLowerCase());
    case "STARTS_WITH" -> text.toLowerCase().startsWith(pattern.toLowerCase());
    default -> false;
};
two details that matter

.find(), not .matches(). Your REGEX pattern is a substring search, not a whole-string match. (?i)\b(loan)\b fires on "I was wondering about a loan for my car". That's usually what you want — just don't be surprised.

The matched row also sets the state. state_code on the winning classifier row becomes the session state (uppercased; blank → UNKNOWN). So a classifier isn't just "which intent" — it's "which intent, starting where".

the collision rule

If two or more distinct intents match the same message, the resolver audits INTENT_CLASSIFIER_COLLISION with the full matched-by-rule map and returns null. It does not pick the highest priority. It hands the turn to the LLM resolver, which is better equipped to disambiguate.

designing classifiers that don't collide

Collisions are the normal failure mode of a growing classifier table — someone adds (?i)\b(status)\b for ORDER_DIAGNOSTICS and it starts stealing turns from PAYMENT_STATUS. The audit stage tells you exactly which classifier_ids fought. Fix it by making patterns more specific, not by deleting one — and if two intents genuinely overlap in language, that's a signal they should be one intent with two states.

7.3 · AgentIntentResolver — the LLM path

Runs only when the classifier came back empty or collided. It builds a prompt from the enabled ce_intent rows (using llm_hint and description), asks for confidence-scored candidates, and applies its own gates. Its audit stages read like a decision log:

stagemeaning
INTENT_AGENT_SKIPPEDDidn't run — sticky intent, mid-schema-collection, or policy said no.

INTENT_AGENT_SCORESEvery candidate with its confidence.
INTENT_AGENT_REJECTEDTop candidate scored below convengine.flow.llm-threshold (default 0.90).

On collision the session moves to AgentIntentResolver.INTENT_COLLISION_STATE, and ResponseResolutionStep short-circuits into AgentIntentCollisionResolver — which renders the "did you mean A or B?" turn instead of trying to answer.

7.4 · Sticky intent

Mid-flow, re-resolving intent on every turn would be actively harmful: a user halfway through a loan application who types "250000" shouldn't trigger a fresh classification. IntentResolutionStep therefore skips resolution while a schema is being collected (INTENT_RESOLVE_SKIPPED_SCHEMA_COLLECTION) or while the intent is explicitly locked (INTENT_RESOLVE_SKIPPED_STICKY_INTENT). session.unlockIntent() is what releases it — SchemaExtractionStep calls it when there's no schema for the current scope.

debugging intent, fast

Pull /audit/{id}/trace and grep for INTENT_. In order you'll see whether the classifier matched, collided, or missed; whether the LLM ran; what it scored; and why it was accepted or rejected. There's no scenario where you have to guess.

8.4 · Asking for what's missing

The natural pairing is a DERIVED response whose hint reads {{missing_fields}}:

ce_response.derivation_hint

{{missing_fields}} and do not claim processing/submission. Otherwise use
context.agent.observations and context.agent.finalAnswer to explain the decision.

The "do not claim processing" clause is there because a model handed a half-filled form will happily say "I'm processing your application now". It isn't. Nothing ran — the planner was skipped precisely because the schema was incomplete.

skipping extraction on purpose

Set input param SKIP_SCHEMA_EXTRACTION and the step hydrates the schema state from existing context without calling the LLM. That's what CorrectionStep leans on for AFFIRM-after-confirmation: the slots are already right, re-extracting from the word "yes" would only damage them.

9.5 · Multi-pass evaluation

Rules don't run once. applyRules(...) loops up to 5 passes, re-fetching eligible rules each time — because a rule that changes state changes which rules are now eligible. It stops early the moment a pass changes neither intent nor state.

engine/steps/RulesStep.java
int maxPasses = 5;
for (int pass = 0; pass < maxPasses; pass++) {
    boolean passChanged = false;
    List<CeRule> allRules = staticCacheService.findEligibleRules(session.getIntent(), session.getState(), phase);
    for (CeRule rule : allRules) {
        if (!typeResolver.resolve(session, rule)) { auditRuleNoMatch(...); continue; }
        actionResolver.resolve(session, rule);
        if (intentChanged || stateChanged) passChanged = true;
    }
    if (!passChanged) break;    // converged
}
the chaining gotcha

This lets you chain A → B → C in one turn. It also means a badly written pair of rules can ping-pong (A→B, B→A) for five passes and land somewhere arbitrary. If you see a state flapping, look for two rules whose scopes overlap in both directions.

every rule decision is audited

RULE_MATCH (matched, with full context and schema snapshot), RULE_APPLIED (after the action, with the resulting intent/state), RULE_NO_MATCH (with a reason: TYPE_CONDITION_NOT_MET or TYPE_RESOLVER_MISSING). Each carries the rule_id. When a flow goes somewhere unexpected, this is a two-minute investigation.

Response resolution

Pick a ce_response row, render it, transform it. The scoring formula is worth memorising — it explains 90% of "why did I get that answer?".

10.1 · Candidate selection and scoring

All enabled ce_response rows matching the current intent (or with a null intent) and matching the current state (or ANY) become candidates, then get scored:

ResponseResolutionStep.responseScore() — verbatim
int exactState  = matches(response.getStateCode(),  session.getState())  ? 1 : 0;
int exactIntent = matches(response.getIntentCode(), session.getIntent()) ? 1 : 0;
int anyState    = matches(response.getStateCode(),  "ANY")              ? 1 : 0;
int anyIntent   = response.getIntentCode() == null ? 1 : 0;
int priority    = response.getPriority() == null ? 999999 : response.getPriority();

return (exactState * 1000) + (exactIntent * 100) + (anyState * 10) + anyIntent - priority;
how to read that

State specificity dominates everything (×1000), then intent (×100), then the ANY fallbacks. priority is subtracted — so lower numbers win. It's a tie-breaker within a specificity tier, not a global override: a priority = 1 row scoped ANY/ANY will still lose to a priority = 500 row scoped to your exact intent and state.

no candidates = hard failure

Zero matching rows throws ConversationEngineException(RESPONSE_MAPPING_NOT_FOUND) after auditing the stage, and the controller returns an ERROR payload. Always seed a catch-all ce_response for (YOUR_INTENT, ANY) while developing.

10.2 · EXACT vs DERIVED

EXACTDERIVED

the DERIVED prerequisite people miss

For DERIVED, the step goes looking for a ce_prompt_template whose output_format equals the response's output_format and whose scope matches. If none exists it throws:

IllegalStateException: No ce_prompt_template found for output_format=TEXT, intent=…, state=…

Template selection uses its own score: (intentScore × 10) + (stateScore × 5), where an exact intent match scores 2 (else 1) and an exact state match scores 2, ANY scores 1, no match scores 0. So an exact-scope template always beats an ANY one.

10.3 · Output formats

TEXT (prose → TextPayload), JSON (structured → JsonPayload), SCHEMA_JSON (schema-constrained JSON — the format used by extraction templates), SEMANTIC_INTERPRET (the semantic layer's interpretation shape). The API payload comes back as {"type":"TEXT"|"JSON","value":…}.

10.4 · Transformers

Two hooks let you reshape the answer without touching the engine:

  • ResponseTransformType.LLM — applied inside ResponseResolutionStep, right after generation. Use for redaction, formatting, or appending citations.
  • ResponseTransformType.FINAL — applied in ConversationController just before serialisation. Use for host-app envelope shaping (adding UI hints, widget descriptors, tracking ids).

Implement ResponseTransformer and register it as a bean; ResponseTransformerService picks it up.

the trail

RESOLVE_RESPONSE (which response_id won) → RESOLVE_RESPONSE_LLM_INPUT/_OUTPUT (if DERIVED) → ASSISTANT_OUTPUT (the final payload plus a full context and schema snapshot). If the answer looks wrong, RESOLVE_RESPONSE tells you whether you got the wrong row or the right row with a bad prompt — two very different fixes.

11.4 · The loop

engine/steps/AgentToolStep.java — the shape of it
int maxLoops = resolveMaxLoops();                     // AGENT_TOOL_MAX_LOOPS, default 5
for (int i = 0; i < maxLoops; i++) {

    AgentPlan plan = planner.plan(session, tools, observations);   // ← one LLM call

    if ("ANSWER".equalsIgnoreCase(plan.action())) {
        writeFinalAnswerToContext(session, plan.answer());          // context.agent.finalAnswer
        break;
    }
    if (!"CALL_TOOL".equalsIgnoreCase(plan.action()))   { /* fallback answer */ break; }
    if (isPolicyRestrictedOperationTag(plan.operation_tag())) { /* blocked  */ break; }
    if (executedToolSignatures.contains(signature))          { /* dup loop */ break; }
    if (nextToolGuardrailBlockReason(toolCode, observations) != null) { break; }

    CeAgentTool tool = registry.requireTool(toolCode, session.getIntent(), session.getState());
    AgentToolExecutor executor = resolveExecutor(registry.normalizeToolGroup(tool.getToolGroup()));
    String rowsJson = executor.execute(tool, args, session);

    observations.add(new AgentObservation(toolCode, rowsJson));
    writeObservationsToContext(session, observations);              // context.agent.observations[]
}

the plan contract

what the LLM must return — schema enforced by AgentPlanner
{
  "action":        "CALL_TOOL" | "ANSWER",   // nothing else is accepted
  "tool_code":     "<tool_code_or_null>",
  "args":          { },
  "answer":        "<text_or_null>",
  "operation_tag": "<POLICY_RESTRICTED_OPERATION_or_null>"
}

normalizePlan() is deliberately paranoid. Any action that isn't exactly CALL_TOOL or ANSWER — including popular hallucinations like clarification_required or needs_clarification — collapses to a safe ANSWER with a fallback message. CALL_TOOL with a null tool code becomes ANSWER with "I couldn't decide the next tool step safely." Unparseable JSON becomes ANSWER with "I couldn't plan tool usage safely. Can you rephrase your question?". The loop cannot be crashed by a bad generation.

the five guardrails inside the loop

11.5 · How the planner prompt is built

Prompt resolution walks a four-level fallback: exact (intent, state) in ce_agent_planner → (intent, ANY) → (ANY, ANY) → ce_config keys SYSTEM_PROMPT/USER_PROMPT under type AgentPlanner. The chosen source is recorded in the audit payload, so you always know which row produced a given plan.

the backtick trick — a genuinely non-obvious feature

AgentPlanner.extractMentionedToolCodes() scans your planner prompts for tool codes in backticks containing a dot — `loan.credit.rating.check`. If it finds any, only those tools are offered to the LLM this turn, even if more are registered for the scope. If none match, all scoped tools are offered (fail-open).

So writing an ordered procedure in your planner prompt using backticked tool codes doubles as a filter. That's why the shipped loan planner prompt lists its four tools in backticks — it's both instruction and allowlist.

observation compaction

Observations grow fast, and re-sending 40 KB of rows on every loop iteration is how you get a slow, expensive, confused planner. So buildObservationsPayload():

  • keeps only the last AGENT_PLANNER_MAX_OBSERVATIONS_COUNT observations (default 2);
  • summarises each down to known signal fields — status, summary, message, error, queryCode, rowCount, valid, canExecute, selectedCase, outcome, finalSummary, graphError …;
  • for row arrays, replaces the payload with rowCount plus a 2-row preview;
  • truncates to AGENT_PLANNER_MAX_OBS_CHARS (default 6000, floor 1000);
  • de-duplicates identical entries, and unpacks nested JSON strings so the model never sees double-escaped payloads.

The audit payload records agent_observations_compacted, _raw_chars and _final_chars — if your planner is confused about data it "saw", check whether compaction dropped it and raise the limits via ce_config.

11.6 · HTTP_API in depth

The most-used group, with four levels of consumer control. HttpApiToolExecutor resolves in this order:

  1. HttpApiProcessorToolHandler — routes through api-processor's RestWebServiceFacade.
  2. HttpApiRequestingToolHandler — you return an HttpApiRequestSpec; the framework owns execution: timeouts, retry with exponential backoff, circuit breaker, auth injection (API_KEY, static BEARER), and response mapping (RAW_JSON, JSON_PATH, FIELD_TEMPLATE, MAPPER_CLASS, TEXT). Start here.
  3. HttpApiToolHandler — plain "here's the tool and args, return an object". You own the call.
  4. HttpApiExecutorAdapter — the legacy single-bean fallback used when no per-tool handler matches.
one bean per tool_code — the recommended shape
@Component
public class CreditRatingToolHandler implements HttpApiRequestingToolHandler {

    @Override public String toolCode() { return "loan.credit.rating.check"; }

    @Override
    public HttpApiRequestSpec requestSpec(CeAgentTool tool, Map<String,Object> args, EngineSession session) {
        return HttpApiRequestSpec.builder()
            .method("GET")
            .url("https://credit-union.internal/v1/rating/" + args.get("customerId"))
            .auth(HttpApiAuthSpec.apiKey("X-Api-Key", System.getenv("CU_KEY")))
            .responseMapping(HttpApiResponseMapping.jsonPath("$.data"))
            .build();
    }
}

Things this run demonstrates that are easy to miss

External MCP servers

A real Model Context Protocol client. Register a server at runtime and its tools appear in the planner's list — no restart, no code.
two different things share the letters "MCP"

Internal Agent tools — ce_agent_tool rows with groups like HTTP_API, executed by an AgentToolExecutor. Fully config-driven, no external process. (These were historically called "MCP tools" and lived in ce_mcp_tool; the tables and classes were renamed to ce_agent_* / Agent*. The YAML prefix convengine.mcp.* still carries the old name.)

The MCP client — engine/mcp. An actual JSON-RPC 2.0 implementation of the Model Context Protocol that talks to third-party servers written in Python, Node, or anything else. That's this section.

why config is DB-backed with no file fallback

Earlier revisions persisted to ~/.convengine/mcp-servers.json. In a horizontally-scaled deployment that file lives on one pod's disk and is invisible to every other replica — so it can't be the source of truth. ce_mcp_server can. A background thread reloads the table every 30 seconds, so a server registered on pod A is usable on pods B and C within one cycle, with zero pod-to-pod communication.

If the table doesn't exist, McpRegistry logs an error and starts with zero configs — the rest of the app still boots, but MCP registration and discovery won't work until you create it.

13.2 · Register a server

13.4 · Discovery is automatic — execution is not

Each discovered tool is synthesised into a tool code:

mcp.<serverId>.<toolName>      e.g. mcp.weather-srv.get_forecast

AgentPlanner.plan() merges McpRegistry.discoveredTools() into the tool list it shows the LLM, wrapped in a try/catch so an unreachable server degrades to "that tool isn't offered this turn" rather than failing the conversation. So a newly registered server's tools appear in the planner prompt with no configuration at all.

the gotcha that costs everyone an afternoon

That automatic merge only changes what the planner sees. To execute one, AgentToolRegistry.requireTool(...) still demands a matching ce_agent_tool row. Without it, the LLM cheerfully picks the tool and the call dies with IllegalStateException: Missing enabled Agent tool for current intent/state.

the row you must add
INSERT INTO ce_agent_tool (tool_code, tool_group, intent_code, state_code, enabled, description)
VALUES ('mcp.weather-srv.get_forecast', 'MCP_SERVER', 'WEATHER_LOOKUP', 'ANY', true,
        'Get a weather forecast for a city');

This is deliberate, not an oversight: a server you connect for one flow must not silently become callable from every other flow in your application. Discovery is convenience; the row is authorisation.

end-to-end checklist

1. POST /servers · 2. GET /servers/{id}/tools shows the manifest · 3. POST …/tools/{tool}/call returns a result · 4. add the ce_agent_tool row for the right intent/state · 5. send a message that lands in that scope · 6. check AGENT_TOOL_CALL in the trace. If step 6 shows nothing, re-read §11.3.

The semantic query pipeline

"How many orders shipped late last quarter?" → safe, read-only SQL. No hand-written templates, and the model never touches your database directly.
optional, Postgres-only, and the most involved feature here

Everything else in this guide works without it. Turn it on with convengine.mcp.db.semantic.enabled: true and populate the ce_semantic_* tables. If you just need "run this one known query", a DB tool with a ce_agent_db_tool SQL template is far simpler.

14.1 · The chain

Three tools, executed by the ordinary planner loop, in a fixed order the planner prompt enforces:

the only supported semantic chain
db.semantic.interpret   → English → a canonical query intent (entities, filters, measures)
        ↓
db.semantic.query       → canonical intent → SQL, using ce_semantic_* mappings
        ↓
postgres.query          → preflight + guardrail + execute, return rows
        ↓
ANSWER                  → planner summarises the rows (Markdown table if tabular)

The order is not advisory. AgentPlanner's default system prompt states it explicitly and rewriteSemanticPlan() repairs a common planner mistake automatically: if the LLM calls db.semantic.query without a canonicalIntent, the planner digs the one produced by the most recent db.semantic.interpret observation out of context and injects it — rather than letting the call fail.

14.2 · The metadata you author

14.3 · The safety stack

Generated SQL passes through four gates before it reaches your database:

  1. Interceptor chain — PostgresQueryInterceptor beans normalise or rewrite SQL. Ships with DefaultPostgresQueryInterceptor at lowest precedence; yours run first.
  2. Preflight — validates against real schema metadata (ce_semantic_source_table / _column, or live introspection) and can auto-repair via a bounded LLM loop (sql-auto-repair-enabled, sql-auto-repair-max-retries). Emits AGENT_DB_PREFLIGHT and AGENT_DB_PREFLIGHT_REPAIR with SQL before/after.
  3. AgentSqlGuardrail — blocks anything that isn't a single read-only statement. No multi-statement, no INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER/CREATE/MERGE/CALL. Single SELECT and WITH only.
  4. Row limits — default-limit: 100, max-limit: 500, plus max-join-hops and max-tables caps on traversal.
SQL observability

Execution emits AGENT_DB_SQL_EXECUTION to both audit and ce_verbose, carrying sql, params, row_count and a rows preview. You can see exactly what ran, with what bind values, for every conversation. Introspection can be fenced with convengine.mcp.db.introspect-tables (exact names or ce_* wildcards).

clarification instead of guessing

If db.semantic.interpret or db.semantic.query returns needsClarification=true, the planner is instructed to stop calling tools and return ANSWER using the supplied clarificationQuestion. The user's reply is then detected as a clarification answer, the pending clarification is cleared, the act is forced to ANSWER, and the chain resumes — rather than a new query being generated from a half-understood question.

Performance — caching and async

The config tables are read dozens of times per turn. They are not queried dozens of times per turn.

16.1 · The static config cache

Add @EnableConvEngineCaching and StaticTableCachePreloader loads every static ce_* collection into memory at startup. StaticConfigurationCacheService then serves rules, intents, classifiers, responses, prompt templates, tools, planners and verbose rows from RAM — turning RulesStep's multi-pass lookups and ResponseResolutionStep's candidate scan into sub-millisecond in-memory filters.

the proxy detail that matters

Every internal helper routes through the proxied bean rather than calling sibling methods directly. Self-invocation bypasses Spring's @Cacheable advice — which is exactly how a "cache" silently re-runs SQL on every call. If you extend the cache service, keep that pattern.

operating the cache without a restart
curl -X POST http://localhost:8080/api/v1/cache/refresh   # flush + reload after a DML change
curl      http://localhost:8080/api/v1/cache/analyze   # prove caching is actually healthy

ConvEngineCacheAnalyzer reports the active CacheManager, provider/resolver/interceptor beans, native entry counts, warmup timings, AOP advisor metadata, and — most usefully — first-call versus second-call latency. If those two numbers are the same, your cache isn't working, and the report tells you which link in the chain is broken.

the workflow this implies

Change a ce_* row → POST /api/v1/cache/refresh → test. Skip the refresh and you'll be debugging behaviour from a snapshot taken at boot. This is the second most common "the engine is ignoring my change" cause, after scope mismatches.

16.2 · Async writes

whathow
Conversation state@EnableConvEngineAsyncConversation — persistence moves off the request path, fronted by a synchronised cache so reads stay correct.
LLM call logsLlmCallLogPersistenceService is @Async. Prompts and completions are large; writing them inline would add latency to every turn.
Conversation historyWritten in PipelineEndGuardStep, decoupled from the audit path.

16.3 · Payload slimming

EngineSession.safeInputParams() strips duplicated heavyweight objects (CONTEXT, SCHEMA_JSON, SESSION_SUMMARY) before JPA serialisation — they're already stored once in context_json, and carrying second copies into input_params_json bloats every conversation row for no benefit.

the framework's own rule

From AGENT.md: "Do not reintroduce synchronous configuration-table lookups into the request path." If you're adding a step, resolve static config through StaticConfigurationCacheService, not a repository.

YAML vs ce_config

Anything resolved through CeConfigResolver can be overridden per-deployment in ce_config without a restart (after a cache refresh). YAML is for infrastructure-shaped settings — timeouts, transports, feature flags. ce_config is for behaviour you may want to tune while running: prompts, regexes, loop limits, observation budgets.

Gotchas — the twelve things that bite people

Roughly in the order you'll hit them.
  1. You forgot the POST_AGENT_INTENT rule

    Symptom: RESPONSE_MAPPING_NOT_FOUND on the very first message. Cause: the classifier set state UNKNOWN and nothing moved it. Every intent needs a rule out of UNKNOWN. §4.

  2. You changed a ce_* row and nothing happened

    POST /api/v1/cache/refresh. The static cache is loaded at boot and is not DB-change-aware. §16.1.

  3. Your tool is registered but never called

    Check context.agent.lifecycle.status — it will be one of the six skip statuses in §11.3. Nine times out of ten it's NO_TOOLS_FOR_SCOPE (state mismatch) or SKIPPED_SCHEMA_INCOMPLETE.

  4. An MCP server tool is offered but explodes on call

    IllegalStateException: Missing enabled Agent tool for current intent/state. Discovery ≠ authorisation. Add the ce_agent_tool row with tool_group='MCP_SERVER'. §13.4.

  5. You wrote NULL for a wildcard scope

    ANY is the wildcard. NULL and blank are rejected by CHECK constraints on the scoped tables, or silently fail to match. §3.3.

  6. You're following docs that say context.mcp.*

    The runtime writes context.agent.*. Older docs, the shipped AGENT.md, and mcp_planner_seed.sql itself still use the old path — a JSON_PATH rule written against context.mcp.finalAnswer will never match. §5.3.

  7. Your DERIVED response throws on a missing template

    No ce_prompt_template found for output_format=…. DERIVED requires a matching template by output_format + scope. EXACT doesn't. §10.2.

  8. Extraction "succeeds" with zeros and empty strings

    A placeholder value counts as present, so schemaComplete flips true and you act on garbage. Your extraction prompt must say "return null, never placeholders", and run at temperature 0. §8.3.

  9. The planner runs out of loops

    toolExecutionAbrupted: true in context and a vague answer. Default cap is 5 planner iterations including the final ANSWER. Raise AGENT_TOOL_MAX_LOOPS via ce_config. §12.

  10. Your priority number "isn't working"

    In ce_response scoring, priority is subtracted (lower wins) and is dwarfed by state specificity (×1000) and intent specificity (×100). It's a tie-breaker within a tier, not an override. §10.1.

  11. The planner ignores tools you registered

    If your planner prompt mentions any backticked tool codes, only those are offered. Add the new tool code to the prompt, or remove the backticks. §11.5.

  12. Two classifiers fight and the LLM bill goes up

    INTENT_CLASSIFIER_COLLISION means the deterministic path returned nothing and every such turn now costs an LLM call. The audit payload names the colliding classifier_ids. §7.2.

the universal debugging move

GET /api/v1/conversation/audit/{conversationId}/trace. Read it top to bottom. Somewhere in that list is a stage that says exactly what the engine decided and why — INTENT_CLASSIFIER_COLLISION, RULE_NO_MATCH with a reason, AGENT_NO_TOOLS_AVAILABLE, RESPONSE_MAPPING_NOT_FOUND. The design goal is that you never have to guess, and in practice you don't have to.
